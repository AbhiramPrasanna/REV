\begin{abstract}
Disaggregated memory splits a cluster into CPU rich compute nodes and capacity
rich, CPU poor memory nodes joined by RDMA. Every ordered index on that substrate
must answer a question that does not arise in a shared memory system: \emph{where
does an index operation execute}. The answer is almost always the same, and it is
almost always fixed at design time. The index caches part of itself on the
compute node and leaves the memory node idle, because memory side CPU is assumed
too scarce to be a participant.

We show by measurement, on two state of the art disaggregated B$^+$ trees, that
this leaves capacity on the table, and that in one case the mechanism to claim it
was already present and unused. DEX possesses both levers, but builds its identity
around the cache and exposes memory side execution as a switch beside it, so cache
size and cache policy are asked to carry all of the work. They cannot, because a
B$^+$ tree presents the cache with two populations whose residency economics have
nothing in common: inner nodes are few and hot and scale with the index, while
leaves are many and scale with the data. Under a uniform access pattern the second
population is not cacheable at any budget, and we measure the consequence
directly. The rate at which DEX's leaf path fails holds at one call per lookup
across a fourfold cache increase and at 1.3748 calls per scan to four decimal
places across an eightfold one. The leaf half of the cache is not returning a
diminishing amount. It is returning nothing, while occupying frames the inner path
could have used.

We then assign each population to the lever that can hold it: cache the inner
path, and serve the leaf from the memory node, gated so that the memory node is
engaged only after the cache has already failed. Both levers stay; each is pointed
at the population it can win. Measured against DEX's own ceiling, thirteen of
sixteen workload cells then exceed, simultaneously on throughput and tail, the
best that design reaches anywhere in an eightfold cache sweep, and on scans the
gated configuration at one eighth of the memory beats the cached configuration at
full memory. The caching lever is not weakened by this but freed: one sided read
traffic on point lookups falls to 0.02\% of what caching alone required, and each
megabyte of cache buys between 1.8 and 4.1 times more throughput, with the largest
correction landing on exactly the workloads where the misallocation was worst.

CHIME, whose compute cache holds internal nodes only, separates the two levers
even more cleanly, because its sweep crosses the point at which its internal index
stops fitting and throughput falls by 3.7 times in a single step. Caching raises
the plateau above that boundary and does almost nothing below it; memory side
execution removes the cliff below it and is exactly inert above it. Used together
they exceed what either reaches alone. Finally we report a deliberate
falsification: an optimisation that shrank the bytes per covered leaf roughly
fortyfold while leaving the number of crossings unchanged lost 41\% of throughput,
and lost 15\% even at a 59\% cache hit rate. Given a path that removes crossings
instead, the same mechanism gains 19\%.
\end{abstract}

\section{Introduction}
\label{sec:intro}

An index on disaggregated memory has two levers against remote cost, and the
literature has largely treated them as rivals.

A \textbf{compute side cache} decides \emph{how often} an operation touches the
network. It is attractive because it is portable: it assumes nothing of the
memory node beyond a region of registered memory, so it survives the strictest
reading of disaggregation, in which the memory node has almost no usable CPU at
all.

\textbf{Memory side execution} decides \emph{what a touch costs}. It runs index
logic on memory node CPUs so that a request returns a result rather than bytes.
It is the lever the literature reaches for last, and the reason is the same
axiom: the memory node is assumed too CPU poor to participate.

Two recent designs illustrate how much can be extracted from the first lever
alone, and they do it in different directions. DEX reduces how often a remote
trip happens, with a path aware compute side cache, pointer swizzling, a scalable
replacement structure and a probabilistic admission policy. CHIME reduces how
much a trip carries and how many trips a search needs, pairing a hopscotch leaf
layout with a compute side cache so that one one sided read covers more of the
search. Both are careful, and both are complete answers within their assumption.

This paper asks what that assumption costs, and it asks it by measurement.

\paragraph{The finding.}
The quantity these designs spend their budget on is not the quantity that bounds
them. A cache can make the expensive path rarer. It cannot make it cheaper, and
on this fabric the cost of a crossing is nearly independent of how many bytes it
carries: a seventy byte read and a five hundred byte read cost about the same.
That has three consequences we measure directly.

First, the caching lever \emph{saturates, and reports its own saturation}. When a
leaf level remote procedure path is available, the rate at which it fires counts
exactly how often the cache failed to resolve the leaf. In DEX under uniform
access that rate is flat: every lookup misses its leaf at the first three cache
points and 99.7\% still do at the fourth, and uniform scans hold at 1.3748 calls
per operation to four decimal places across the entire eightfold sweep. More
memory is not producing a diminishing return there. It is producing no return.

Second, where the cache does have a residency boundary to cross, the design falls
off it. CHIME caches internal nodes only, and its internal index is roughly 90 to
100 megabytes at the geometry we use. Above that budget its throughput is flat and
good; one step below it, uniform point throughput falls by a factor of 3.7.

Third, both effects are removed by the same change, and it is a small one:
convert a leaf level cache miss into a request that the memory node answers, and
gate that conversion on the miss so that the memory node is engaged only when the
cache has already failed. In DEX this puts thirteen of sixteen workload cells past
the best that design reaches anywhere in an eightfold cache sweep, on throughput
and tail simultaneously. In CHIME it removes the cliff entirely while remaining
exactly inert above the boundary.

\paragraph{Levers, not knobs.}
The two levers turn out to be complementary in a regime sense rather than
substitutes. Caching raises the plateau where the working set fits and does
almost nothing below it. Memory side execution removes the cliff below the
boundary and contributes nothing above it. They act on disjoint parts of the same
curve, which is why a system that owns both and never asks which regime it is in
can still collapse, and why the pair reaches an operating point that neither
reaches alone.

\paragraph{Contributions.}
\begin{itemize}
  \item A measurement study of two state of the art disaggregated B$^+$ trees
    that locates, in each, the point at which the caching lever stops returning
    value, and shows that each design already carries a signal reporting it
    (Sections~\ref{sec:dex} and~\ref{sec:chime}).
  \item \emph{Run at a time scan pushdown}: a range scan served in a constant
    number of network round trips rather than one per covered leaf, by executing
    the leaf chain traversal at the memory node and returning a run of results in
    a single reply. Scans are the case where the caching lever is structurally
    unavailable, and no prior disaggregated index offloads one as a run
    (Section~\ref{sec:dex:add}).
  \item \emph{Encoding agnostic memory side execution}: the demonstration that
    pushdown requires only that the memory node speak the index's own node
    encoding, not that the index store plain records. We establish this by
    instantiating one execution path on two incompatible encodings, one of which
    exists precisely to make one sided reads safe without memory side CPU
    (Section~\ref{sec:chime:add}).
  \item \emph{The lever map}: a measurement separating the two levers by regime,
    showing that one owns the plateau and the other the cliff, and that their
    combination exceeds the unmodified design's own ceiling on a quarter of the
    memory it needs to reach that ceiling (Section~\ref{sec:chime:map}).
  \item A falsification test of the underlying account. Crossings and not bytes
    are the currency, which forbids a specific and tempting optimisation. We built
    that optimisation, measured the predicted loss, explained it, and repaired it
    (Section~\ref{sec:chime:falsify}).
\end{itemize}

\section{Background}
\label{sec:bg}

\paragraph{Disaggregated memory.}
A disaggregated cluster separates compute nodes, which have many cores and little
memory, from memory nodes, which have much memory and few cores, and joins them
with RDMA. One sided verbs let a compute node read or write remote memory without
involving the remote CPU; two sided verbs require a thread on the far side to
receive and act. Because memory side cores are the scarce resource, one sided
access is the default, and a design that requires memory side threads has to
justify them.

\paragraph{Why disaggregated indexes cache inner nodes.}
An index operation walks from a root to a leaf, and each level not held locally
costs a round trip. Caching the upper levels is unusually attractive on this
substrate because inner nodes need no coherence: a stale inner node sends the
search to the wrong leaf, which the operation detects and retries, so a compute
node may hold an out of date copy without returning a wrong answer. Leaves have
no such property, and several designs therefore exclude them from the cache
rather than pay for cross node invalidation.

\paragraph{The two systems.}
\emph{DEX} caches both inner and leaf pages under a path aware policy, so that a
cached path is contiguous from the root downward, and admits leaves only
probabilistically because leaf residency scales with the data rather than with
the index. It offloads point operations at the cache boundary under a runtime cost
model, and it decomposes a range scan spanning several leaves into repeated single
key lookups, because it deliberately maintains no leaf links.

\emph{CHIME} caches internal nodes only and spends its remaining design budget on
making the one unavoidable remote leaf access smaller: a hopscotch leaf layout
confines a key to a short neighbourhood so a reader fetches a segment rather than
a whole leaf, a hotspot structure remembers where a hot key sits so the read
shrinks to a single entry, and a replicated per group metadata copy makes a
partial read self describing. Its leaves also carry per cacheline version bytes,
so a one sided reader can detect a torn read without taking a lock.

Every one of CHIME's mechanisms reduces bytes. None reduces crossings. That
distinction is the subject of this paper.

\subsection{Every comparison is a system against itself}

Both studies are ablations. The two configurations in every figure are one
runtime setting apart on one binary, running the same workload generator against
the same tree with the same thread count on the same hardware. Nothing else
differs, so every movement is causally attributable to the setting.

We deliberately report no cross system numbers. Such a comparison must equalise
the dataset, the cache accounting, the thread count and the latency definition
across codebases that measure each differently, and every one of those
equalisations is a place where an effect can be manufactured or hidden. A per
thread cache and a shared cache are not the same quantity; a system driving
clients from one machine and a system running the same binary on two nodes do not
mean the same thing by a thread count; a mean and a tail are not interchangeable.
The claims here are factors of two to six between two configurations of one
binary, and a comparison whose thread accounting is off by a factor of two can
move a ratio by as much as the effect being claimed. Section~\ref{sec:limits}
states what we would fix before adding one.

\subsection{What replaces an external reference}

Removing the external baseline removes a line from a chart, so something must say
whether a movement is large. Three quantities do, and all three are internal to
the system under test.

\begin{enumerate}
  \item \textbf{The design's own ceiling.} The best value the unmodified design
    reaches at \emph{any} cache size in the sweep. A configuration that exceeds
    that ceiling has done something more memory could not do.
  \item \textbf{Cache equivalence.} How much cache the unmodified design would
    need to reach what the modified one reaches at the smallest budget swept.
    This is the provisioning question stated without reference to anyone else.
  \item \textbf{Crossings per operation.} Network round trips, counting both one
    sided reads and remote procedure calls. This is what the fabric charges for,
    it is measured directly rather than inferred from throughput, and it is the
    mechanism behind the other two.
\end{enumerate}

\subsection{Setup}

Both studies run on the same two node RDMA cluster, one compute node and one
memory node. The workload matrix is four cells in each: point lookup and hundred
key range scan, crossed with uniform and Zipfian key distributions at skew 0.99.
Both bulk load fifty million keys and measure a read only workload, so nothing
here bounds insert, update or delete behaviour.

DEX runs thirty six compute threads against four memory side service threads and
sweeps its compute side cache across 64, 128, 256 and 512 megabytes, giving
sixteen cells per configuration. Latency is read from the per operation
histogram in each run's own log rather than from an aggregate, so a tail is a
measured tail.

CHIME runs thirty four application threads per node against four memory side
threads. Its sweep is larger because it has two levers to cross: four cache
budgets against leaf caching off and on against memory side execution off and on,
over the same four workloads, for sixty four cells and roughly six hours per
node. Its leaf cache is carved \emph{out} of the total budget rather than added to
it, so every arm occupies identical compute side memory and caching leaves must
earn its share against the inner nodes it displaces.

\section{DEX}
\label{sec:dex}

\subsection{A design that had both levers and leaned on one}

DEX pulls the caching lever hard and well. Its compute side cache holds both
inner and leaf pages under a path aware policy, so that the resident portion of a
root to leaf path is contiguous and a traversal degenerates into local pointer
chasing for as long as the path stays resident. Replacement avoids the
centralised structures that would serialise under the replacement rate a
disaggregated setting produces. Admission is probabilistic and asymmetric: inner
nodes are always admitted, leaves only one time in ten.

\emph{DEX also has the second lever.} It can offload an operation at the cache
boundary when a runtime cost model judges a remote call cheaper than the
remaining descent. That is what makes it the instructive subject rather than a
foil: the mechanism is present, and the design does not build its identity around
it. The cache is the system. Offloading is a switch beside it.

The consequence is that cache \emph{size} and cache \emph{policy} are asked to
carry all of the work, and the design's own policy shows the strain. Refusing
nine leaves in ten is not a tuning constant arrived at arbitrarily; it is the
design reporting that caching leaves usually does not pay, and then hedging the
report with a probability rather than acting on it.

\subsection{Two node classes, one lever}
\label{sec:dex:classes}

The hedge is necessary because a B$^+$ tree presents the cache with two
populations whose residency economics have nothing in common.

\textbf{Inner nodes} are few, and their count scales with the \emph{index}. Every
operation touches the same handful near the root, so they are hot by
construction, and a modest budget holds the whole upper path. This is the ideal
case for a cache, and DEX admits them unconditionally for exactly that reason.

\textbf{Leaves} are many, and their count scales with the \emph{data}. Fifty
million keys produce millions of leaves. Whether they are cacheable at all
depends entirely on the access pattern: under skew a hot subset exists and a
cache can capture it, and under a uniform pattern every leaf is equally likely
and there is no subset to capture at any budget.

DEX applies one lever to both populations and manages the mismatch with a
constant. That works while the second population happens to be cacheable. Where
it is not, the budget spent trying is not merely unproductive, it is
\emph{contested}: leaf frames and inner frames come from the same pool, so a
megabyte spent on a leaf that will not be revisited is a megabyte unavailable to
the path that would have been.

\subsection{Under uniform access, the leaf half of the cache returns nothing}
\label{sec:dex:sat}

The first measurement is the cache sweep with memory side execution absent.
Across an eightfold increase, from 64 to 512 megabytes, uniform scans move from
0.42 to 0.56 million operations per second and uniform lookups from 1.29 to 2.52.
Tail latency moves less than throughput on every workload, and much less on
scans: the two scan workloads never get their 99th percentile below 92
microseconds anywhere in the sweep.

a lever that is disconnected, rather than spending the budget on the population
that is cacheable and serving the other population a different way.

\subsection{Assigning each population to the lever that can hold it}
\label{sec:dex:add}

The response is not to abandon caching. It is to stop asking one lever to serve
two populations with incompatible economics, and to divide them by which lever
can actually hold each. \textbf{Cache the inner path}, whose residency scales with
the index and which is hot by construction. \textbf{Serve the leaf from the memory
node}, whose residency scales with the data and which under uniform access cannot
be made resident at any budget. Both levers stay, and each is pointed at the
population it can win.

Mechanically the change is small and it converts one event. In the design as
built a leaf level miss pulls a page across the network, installs it, and reads
eight bytes out of it. We make that same miss dispatch a request that the memory
node answers. The descent above the leaf, the cache, the admission policy and the
binary are otherwise unchanged.

For a point lookup the memory node searches the leaf in place and returns the
value, so one request replaces one page transfer and the page is never
materialised on the compute node.

For a range scan the change is larger in kind, and it is the contribution rather
than a configuration. Instead of asking for one leaf, the compute node sends the
number of keys still outstanding, and the memory node walks forward along the
sibling chain in its own local memory, gathers matching pairs from as many leaves
as the request needs, and packs them into a contiguous region that the compute
node retrieves with a single read. A scan that spanned a dozen leaves cost a
dozen serial crossings and now costs a constant number, independent of how many
leaves it covers. If the range extends past the last key returned, the traversal
resumes and the remainder is served the same way. This is the mechanism the
decomposition into repeated lookups precludes, and it is available to any index
that can walk its own leaves.

\paragraph{The gate is the whole idea.}
The memory node is engaged only on a miss, so its CPU demand scales with the
\emph{miss} rate rather than with the operation rate. Read as knobs, cache and
memory side execution are substitutes, since more cache means the remote path
fires less often. Read as one structure they are complements: more cache does not
idle the remote path, it \emph{shrinks the bill} that path sends. That is the
difference between this composition and an unconditional pushdown design, which
would pay one request per operation forever regardless of what the cache already
held.

The structure is hybrid along two axes at once. Across the tree it is one sided
above the leaves and result shipping at the leaves, so the inner path remains a
pure caching workload with an idle memory node and only the one level that
caching handles worst is offloaded. Within a single scan it is hybrid per
operation: the resident prefix of a range is scanned locally and costs the memory
node nothing, and only the uncached tail is offloaded.

Both axes move favourably everywhere, so this is a relocation rather than a

\paragraph{The cache is not weakened by this. It is freed.}
The most direct evidence that the division of labour is the right one is what
happens to the caching lever once it stops competing with the leaf population.
At the largest cache, one sided read traffic on point lookups falls to
\textbf{0.02\%} of what caching alone required: 3.34 reads per operation become
0.0008, with a single request carrying the leaf. The inner path is now entirely
resident. The cache did not become less important; it became able to hold the
thing it was always good at holding.

\paragraph{Against the design's own ceiling.}
The strict test is to take the best throughput the unmodified design reaches at
\emph{any} cache size and count how many cells the second lever puts above it.
Thirteen of sixteen clear that bar on throughput, fourteen on tail, and
\textbf{thirteen on both simultaneously}. All eight scan cells clear it. The three
that do not are lookups at the smallest budgets, where the caching lever still has
room to work.

\paragraph{Cache equivalence.}
Figure~\ref{fig:dexequiv} states the provisioning consequence. On scans the gated

an eighth of the memory buys a strictly better point and the equivalent cache for
the caching lever lies beyond the end of the sweep. On uniform lookups the
crossing is inside the sweep: a quarter of the memory suffices. Only on Zipfian
lookups does the caching lever hold its own, which is the expected place for it to
do so, because skew is what makes a working set cacheable at all.

\end{figure}

\paragraph{Why the effect is this large.}
A miss costs 14.25 microseconds when it is a page and 7.27 when it is an answer,
and the 99th percentile of an offloaded operation is 14.0 microseconds, roughly
half the 26.5 microsecond floor the design reaches anywhere in the sweep by
rationing. The mechanism the design declined to build is, on its own, faster than
anything rationing achieved. Cache changes how often the toll is paid; it cannot
change the toll.

\subsection{What it costs}
\label{sec:dex:cost}

The bill is four memory side service threads against thirty six compute threads,
and two properties make it defensible.

First, it is gated by misses rather than by operations, so it shrinks as the
compute side becomes self sufficient. More cache does not strand the mechanism;
it reduces what the mechanism is asked to do.

Second, it saturates early. With the remote path disabled the memory node is
idle and throughput is flat in thread count, which is the control confirming that
the threads do nothing without the path. With it enabled, two service threads
under serve the request stream and four do not: lookup tails fall from 22.5 to
13.5 microseconds between two and four threads and then stop moving at six. Scan
tails do not respond to thread count at all, staying within one histogram bucket
across two, four and six threads, which places the scan tail in the cost of the
offloaded traversal itself rather than in queueing for a service thread.

\subsection{What DEX should have done}
\label{sec:dex:should}

Nothing in this section asks for a mechanism DEX did not have. It asks for the
mechanism it had to be treated as part of the design rather than as a switch
beside it.

\paragraph{The two node populations should have been assigned to different
levers, not managed with one constant.}
This is the whole of it. Inner residency scales with the index and is cacheable;
leaf residency scales with the data and, under a uniform pattern, is not
cacheable at any budget. A design that recognises the split points each lever at
the population it can win and spends the entire compute side budget on the one
that responds to it. DEX instead applies caching to both and reconciles the
mismatch with a probability. That is a smaller version of the right answer, and
it leaves the design dependent on cache size and cache policy for outcomes that
neither can deliver: it is exactly the workloads where the mismatch is worst,
uniform scans and uniform lookups, that the correction improves most
(Table~\ref{tab:productivity}).

\paragraph{The admission constant should have been read as a diagnosis, not a
setting.}
Refusing nine leaves in ten is a correct empirical finding about leaves. What
follows from it is not a smaller number, it is a different venue for that
population, and the design already contained one. The finding and the mechanism
that answers it sit in adjacent parts of the same system and are never connected.

\paragraph{The venue decision should have been evaluated per operation class, not
per node miss.}
DEX's cost model fires at a single miss and compares one request against one
descent. It never asks whether the caching lever is succeeding for a class of
operation as a whole, so when leaf caching degrades the design keeps making
locally reasonable decisions while the aggregate regime has changed underneath
it. The signal it would need is not subtle and the design already produces it: a
leaf failure rate that does not move as the cache grows
(Section~\ref{sec:dex:sat}).

\paragraph{The scan path should not have been traded for pointer simplicity.}
Dropping leaf links keeps pointer management uniform, at the price of turning
every multi leaf scan into a sequence of independent descents. That price falls
on the one operation class where the caching lever is structurally unavailable,
because a scan streams through leaves it will never revisit. A leaf run mechanism
used only on the offload path, never in the cached structure, keeps the
simplification and still allows one reply to carry a run.

\paragraph{What this would have bought.}
Not a different index. The same index, operating at between 1.7 and 2.6 times the
throughput at the same memory, reaching a better point on scans with an eighth of
it, and getting between 1.8 and 4.1 times more out of every megabyte it does
spend. The capacity was available inside the design as published. It was not
taken because one of the two levers was treated as an option rather than as half
of the structure.

\section{CHIME}
\label{sec:chime}

\subsection{The design as built}

CHIME is the harder subject and the better control, because it economises in a
different direction and because its whole structure is built around the memory
node doing nothing.

Its compute cache holds internal nodes only. This is deliberate: excluding leaves
avoids cross node coherence entirely, at the price that the leaf is always a
remote access even when the cache resolved the whole descent. Everything else in
the design makes that unavoidable access smaller. A hopscotch layout confines a
key to a short neighbourhood so a reader fetches a segment rather than a whole
leaf. A hotspot structure remembers which slot a hot key occupies so the read
shrinks to a single entry. Replicated per group metadata makes a partial read self
describing. Per cacheline version bytes let a one sided reader detect a torn read
without a lock.

Two further choices set how badly the design behaves when its bet fails. The
internal fanout is small, chosen so that an internal node is smaller than a leaf,
which makes the tree deep: in our runs the root sits seven levels above the
leaves. And the internal index is roughly 90 to 100 megabytes at this geometry.
Together they mean a cache hit costs one leaf access while a cache miss costs
about seven crossings, so the design is excellent above its residency boundary and
falls a long way below it.

\subsection{Adding both levers}
\label{sec:chime:add}

We add memory side execution on the same gate as in DEX, and we add a compute
side cache for leaves so that the caching lever can reach the last crossing as
well. Both are runtime settings, so one build serves every cell of the sweep.

\paragraph{Encoding agnostic execution.}
CHIME's leaves are not plain records. They are version encoded per cacheline and
their metadata is scattered across entry groups, precisely so that a one sided
reader can validate them without a lock. A memory node that wants to answer a
request about such a leaf cannot simply point at it. It must take a private
snapshot, check that the snapshot is internally consistent, undo the scattering,
and retry if a concurrent writer intervened. The snapshot has to come first:
comparing version bytes in place would let a writer land another cacheline between
the check and the read.

This is the general point. Memory side execution does not require an index to
store plain records; it requires the memory node to speak the index's own
encoding. The traversal logic above that decoding step is identical in both of our
subjects. Only the decoding differs, and it is confined to a single function. An
index whose node format was designed to make memory side CPU unnecessary can still
use memory side CPU.

\paragraph{Structural gating.}
CHIME caches only the level immediately above the leaves, which makes the miss
gate a property of the structure rather than a policy: a cache hit resolves the
descent completely and therefore cannot reach the offload path at all. The gate
is validated independently by comparing the observed offload fraction against the
miss rate predicted from cache occupancy, and the two agree at three separate
budgets, at 63\% against a predicted 60\%, 65\% against 62\%, and 83\% against
81\%. The memory node is busy because the cache is missing, not because the policy
is loose.

\paragraph{Leaf caching and its coherence.}
A leaf served out of local memory is the one read in CHIME that is not self
validating, so it needs a coherence protocol. Each leaf carries a small,
globally unique, never reused stamp that a writer publishes under the leaf's own
lock before it modifies any data. A reader may serve a cached copy only while a
single small read of the leaf's lock and stamp still shows the leaf unlocked and
carrying the stamp the copy was taken at. Because the writer's operations travel
in order on one connection, this makes the check conclusive rather than
heuristic, and because a filling read can close the same check around the data it
fetches, populating the cache costs the round trip the uncached read would have
cost anyway. The cache is never weaker than the one sided path it replaces.

\subsection{The lever map}
\label{sec:chime:map}

The sweep crosses the residency boundary, which is what Arm one could not do, and
the analysis step that makes it legible is to index results by the \emph{inner}
cache rather than by the total. Inner cache is what the caching lever spends on
the descent, and the leaf arm halves it. Re indexed that way the two arms become
commensurable: a leaf enabled cell at 128 megabytes total and a leaf disabled cell
at 64 megabytes total both run a 64 megabyte inner cache, and they measure 0.645
and 0.632 million operations per second, within two percent of each other despite
one holding twice the total memory. Performance here is a function of the inner
budget and the total is close to irrelevant.

\begin{figure*}[t]
  \centering
  \includegraphics[width=\textwidth]{fig_lever_map.pdf}
  \caption{The lever map. Compute node throughput against inner node cache, which
  is what the caching lever spends. The shaded band is where the internal index
  stops fitting. Caching raises the right hand plateau and does almost nothing to
  the left of the band; memory side execution raises the left hand floor and is
  inert to the right of it. The two levers act on disjoint parts of the curve.}
  \label{fig:levermap}
\end{figure*}

Figure~\ref{fig:levermap} is the result, and each lever has a signature.

\textbf{Caching raises the plateau.} Adding the leaf cache lifts Zipfian point
throughput from 2.857 to 3.999 million operations per second, a 40\% gain, and
batched Zipfian scans from 0.500 to 0.594, a 19\% gain. To the left of the band it
does essentially nothing: 1.091 becomes 1.250.

\textbf{Memory side execution removes the cliff.} At a 64 megabyte inner cache,
Zipfian point throughput goes from 1.091 to 2.727. To the right of the band it is
\emph{exactly} inert, holding 2.857 across three consecutive cache points. That
flatness is the gate working as specified.

\textbf{Together they exceed what either reaches.} At a 32 megabyte inner cache
with 32 megabytes of leaf cache, Zipfian point throughput reaches 3.157. The
unmodified design's ceiling is 2.857 and it needs at least a 128 megabyte inner
cache to hold it. The pair therefore delivers 1.11 times the best the design ever
reaches, on half the total budget and a quarter of the inner budget.

\paragraph{One lever can make things worse, and the other bounds it.}
At a 128 megabyte total budget the leaf arm runs a 64 megabyte inner cache, below
the band, and uniform point throughput falls from 2.307 to 0.645. That is a
factor of 3.6 lost by spending budget on the wrong lever. With memory side
execution enabled the same cell recovers to 1.714. The second lever is therefore
not merely additive: it bounds the downside of using the first one aggressively,
which is what makes an aggressive caching policy safe to adopt at all.

\paragraph{Where it does not hold.}
The headline is a Zipfian result. Under uniform access both levers at a 32
megabyte inner cache reach 1.666 against an unmodified plateau of 2.307, so the
pair removes the cliff but does not exceed the ceiling. And on uniform scans leaf
caching is a net loss at every budget we swept, costing 21\% at the largest,
because a uniform scan streams through leaves it will never revisit and there is
nothing for that lever to hold.

\subsection{A falsification test}
\label{sec:chime:falsify}

The account underlying all of this is that crossings and not bytes are the
currency. That claim forbids something specific: an optimisation that shrinks the
bytes a crossing carries, applied where the baseline already spends exactly one
crossing, must not help, and must not be rescued by a high hit rate either.

CHIME's scan path is exactly that setting, since it spends one read per covered
leaf. Our first leaf cache did shrink those reads, from roughly a kilobyte to a
small validation probe on a hit, a factor of about forty, while leaving the
crossing count untouched: the probe is still issued per covered leaf. The account
predicts a regression, and the measurement delivered one of 41\% on uniform scans.
More tellingly it also lost 15\% on Zipfian scans \emph{at a 59\% hit rate}, which
rules out the obvious alternative explanation that the cache was simply too small.

\begin{figure}[t]
  \centering
  \includegraphics[width=0.94\linewidth]{fig_scan_repair.pdf}
  \caption{The falsification test and its repair. Shrinking the bytes per covered
  leaf by roughly forty times while leaving the crossing count alone loses
  throughput, and loses it even where the hit rate is 59\%. Removing crossings
  instead turns the Zipfian arm from a regression into a gain.}
  \label{fig:scanrepair}
\end{figure}

The repair follows from the same account. The set of leaves a scan covers is
known before any network operation is issued, so the validations need not be
serial: one batch validates every resident leaf and a second fetches the rest,
taking a twelve leaf scan from twelve crossings to two. Figure~\ref{fig:scanrepair}
shows the result. The Zipfian arm moves from a 15\% loss to a 19\% gain and the
uniform arm from a 41\% loss to a 21\% loss. The leaf arm gains between 35\% and
40\% in all four cells, and the near uniformity of that gain is itself evidence: a
crossing count fix should appear as a flat multiplier that does not depend on hit
rate, and it does.

The point path is untouched by the repair and reproduces across two independent
six hour sweeps to four decimal places, so run to run noise where the index fits
is negligible and the scan movements are signal. In the stressed cells noise runs
five to twelve percent, and small differences there should not be read.

\subsection{What CHIME should have done}

\paragraph{It should not have bet the design on the index fitting.}
Inner node caching gives a plateau that is flat and good and a cliff that is a
factor of 3.7 deep, with no second lever to catch it. The data shows the catch is
cheap: memory side execution restores most of the loss and is exactly inert above
the boundary, so it costs nothing when it is not needed. A system with one lever
must be provisioned for its worst case; a system with two can be provisioned for
its common case.

\paragraph{It should have priced the exclusion of leaves rather than assuming it.}
Excluding leaves avoids coherence entirely, and the price is one guaranteed
crossing per operation forever. Our stamp protocol shows that price was
mis estimated, since coherence for a cached leaf costs one small probe folded into
a crossing the read needed anyway. Stated carefully, because our own map
complicates it: the leaf lever pays only for point lookups under skew and for
batched Zipfian scans, and it is a loss on uniform scans. The recommendation is
not that leaves should be cached. It is that the coherence argument alone never
settled the question, and the answer is regime dependent.

\paragraph{It should have batched its scan path regardless of any lever.}
The set of covered leaves is known before any network operation is issued, yet the
unmodified path issues one read per leaf, serially. The information needed to
batch was already in hand and unused. This is the cheapest structural improvement
available in the design, it requires no memory side CPU and no coherence protocol,
and it is what made leaf caching viable for scans at all.

\paragraph{It should have reported against its residency boundary.}
Throughput against total cache hides a factor of 3.7 cliff and makes the two
caching arms incomparable; throughput against inner cache makes the structure
legible immediately. The distinction between nominal and effective index cache
matters for the same reason, since a hotspot structure silently claims part of the
nominal budget.

\section{Discussion}
\label{sec:discussion}

\subsection{Three design rules}

The two studies converge on the same three rules, and they are properties of
execution venue rather than of B$^+$ trees.

\paragraph{Ship answers, not pages, but only where caching loses.}
The inner path is where caching wins and should stay one sided and memory node
free. The leaf level is where caching structurally cannot win, because leaf
residency scales with the data rather than with the index. Choosing the venue per
level is what keeps the memory node idle for the majority of the work.

\paragraph{Gate the remote venue on evidence the index already has.}
A miss is a free and exact signal that the compute side cannot answer locally.
Conditioning remote execution on it makes the cost self limiting, which is what
separates this from unconditional pushdown: cache and memory side execution become
complements, and adding cache reduces the memory node bill instead of stranding
the mechanism.

\paragraph{Make the venue decision per operation, not per system.}
The within scan behaviour is the sharpest evidence. A scan whose prefix is
resident is served entirely locally and costs the memory node nothing; only the
uncached tail is offloaded.

\subsection{When the second lever is the wrong answer}

It is inert where caching succeeds, and that is by construction rather than by
luck: in CHIME above the residency boundary it holds one number across three
consecutive cache points. Where a hot set exists and fits, rationing is the right
lever, and our own measurements show the cached configuration winning outright on
Zipfian lookups. A design that always offloads would spend memory node CPU in
exactly the regime where it buys nothing.

\subsection{Limitations}
\label{sec:limits}

\paragraph{Scan tails.}
The second lever improves scan tails substantially but they remain several times
lookup tails, because an offloaded scan walks several leaves on the memory node
and that work sets the floor. Separately, CHIME's leaf caching arm gains
throughput on Zipfian scans while its tail moves the wrong way, plausibly because
batching replaces several small stalls with one larger one. We report this rather
than quoting the throughput alone.

\paragraph{Reads only.}
Both sweeps are read only, so nothing here bounds insert, update or delete
behaviour, and the leaf coherence protocol is exercised but idle: no cached copy
was ever refused during a measured run. A write mixed workload is the measurement
that would give that protocol meaning.

\paragraph{Scale out.}
Both studies use one compute node and one memory node. Self limiting per compute
node is not the same property as bounded across many, and the memory tier is
fixed while compute nodes are not. The gate predicts that aggregate demand should
scale with total misses rather than with total operations, which is a smaller and
more compressible quantity, and that prediction has an obvious falsifier.

\paragraph{No cross system comparison.}
For the reasons in Section~\ref{sec:method}. Adding one requires the four
equalisations stated there to be fixed and reported, the same latency statistic on
both sides, and a sweep run for that purpose rather than assembled from sweeps
that happened to exist.

\section{Related Work}
\label{sec:related}

Disaggregated ordered indexes have converged on compute side caching with one
sided access. Sherman caches only the lowest inner levels and accepts one remote
access per leaf; SMART makes a similar trade for a trie. Both exclude leaves from
the cache for the coherence reason discussed in Section~\ref{sec:bg}, and neither
executes index logic on the memory node. DEX extends caching to leaves under a
path aware policy with probabilistic admission, and adds a cost model that
offloads point operations at the cache boundary, which makes it the closest prior
work and the reason we treat it as the primary subject rather than as a foil.
CHIME attacks trip shape instead of trip frequency. Designs that push computation
into the memory tier exist outside the index literature, generally with
unconditional policies, which is the behaviour our gate is contrasted against.
What is absent from all of them is a scan served as a run rather than as a
sequence of independent descents, and a venue decision conditioned on evidence
that the cache has already failed.

\section{Conclusion}
\label{sec:conclusion}

Taken exactly as built, both of our subjects walk along a curve that more memory
moves them only a little way down, and in neither case is the cause a cache that
is too small. It is that a cache changes how often the remote toll is paid and
never what the toll is. DEX says so itself: at the largest cache only 0.31\% of
uniform lookups are served without leaving the compute node, and the rate at which
its leaf path fires does not fall at all under uniform access across an eightfold
sweep. CHIME says so differently, by falling a factor of 3.7 in one step when its
internal index stops fitting.

Converting one event, a leaf level miss, from a page transfer into an answer, and
gating that conversion on the miss itself, puts thirteen of sixteen DEX cells past
the best that design reaches anywhere in its sweep, on throughput and tail at
once, and on scans buys a better operating point at one eighth of the memory. In
CHIME it separates the two levers by regime, and their combination exceeds the
unmodified ceiling on a quarter of the inner cache needed to reach it.

The account behind those results is falsifiable and we tried to falsify it. An
optimisation that removed bytes without removing crossings lost 41\% of
throughput, and lost even where more than half of its lookups hit. The same
mechanism, given a path that removes crossings instead, gains 19\%. Crossings are
the currency, the execution venue is what sets them, and it should be a runtime
decision rather than a constant chosen when the index was designed.
